# Plan — P3 Decide & write

> Phase P3 of `refdocs/plant-load-radar-PRD.md` §6. Execution doc: `refdocs/execution/2026-10-08-p3-decide.md`. ADR: D-18.

## Why this exists

The pitch's promise is "agents do the legwork, a calculator does the maths, and **people make the call**" (slides 3, 7, 10). Today the board shows a recommendation with the Approve and Change buttons switched off, so the most important sentence of the pitch, *nothing is sent or committed without a person*, is a slogan and not something a judge can click. P3 makes it real: a named scheduler approves or changes the decision, the ringgit on both sides is logged to an append-only ledger, the writer drafts the huddle brief and the customer reply from calculator output, and "ask the board" answers a plain question by running the calculator.

## What's already covered (no work needed)

- The recommendation, its ringgit on both sides and the build-ahead alternative: `src/core/planner.ts`, `src/data/board.ts` (P1).
- The figure registry and the honesty test that fails on any number the model cannot account for (P1, reused by P2 and P2b).
- A ledger row shape with a named-approver rule: `LedgerRowSchema` (P0). It holds one served and one deferred request; the week-43 decision defers three, so the schema is extended (ADR D-18).
- The no-key rule (D-17): drafts are templated, behind an interface a model could fill later.

## Scope

**In:**
- **Ledger:** an append-only JSON Lines file, written only by a server action after a named person approves. Read back and validated on every load. Path from `PLR_LEDGER_PATH` (default `.ledger/ledger.jsonl`, gitignored).
- **Decisions page (`/decisions`):** the pending decision with its ringgit on both sides, **Approve** (record the recommendation) and **Change** (the scheduler picks which request to serve instead; the calculator recomputes both sides), a required approver name, an optional note, and the drafts below. The server recomputes everything; the form sends only the week, the mode, the chosen request, the name and the note.
- **Ledger page (`/ledger`):** every decision with the date, who approved, mode, what was served and deferred, the ringgit on each side, and the **ringgit at stake** (labelled as value at stake, not savings).
- **Writer (templated):** a weekly huddle brief and a reply to the deferred outside customer offering the next free week, built from the recommendation's figures. An interface (`Drafter`) so a model can replace the templates later. Marked "drafted by a template; not sent".
- **Ask the board (`/ask`):** "Can we take N m³ for a party in week W?" as a plain GET form answered by the calculator (fits / fits only by contesting pending requests / does not fit, and the next week that does). No client code, no free-text understanding claimed.
- **Board:** the inert buttons become a link to `/decisions`; the "Decisions waiting" tile subtracts decided weeks; a "Ringgit at stake in logged decisions" tile reads the ledger. The board and the new pages read the ledger at request time, so they are dynamic.

**Out (and why):**
- **Sending anything.** There is no WhatsApp or Power Automate integration (D-11). "Approve" records the decision; the reply is copy-only text and the page says so.
- **A language model for drafts or questions** (D-17).
- **Auth, multiple users, edit or delete of ledger rows.** Named approver by typing a name; the ledger has no update path (D-04, D-11).
- **A "protected this month" figure.** It would be a benefit claim; the page shows ringgit at stake instead (business review, 2026-10-08).

## Approach

The write path is the dangerous part, so it is built first and tested hardest: a pure function `recordDecision` takes the scenario, the request (week, mode, chosen served id, approver, note) and an injected store, recomputes the recommendation itself, refuses an empty name, an unknown or already-decided week, or a chosen request that is not competing in that week, and appends exactly one row. The server action is a thin wrapper. The drafts and the answers are strings built from the same figure registry as the board, so the existing honesty test applies unchanged.

## Risks & unknowns

| Risk | Mitigation |
|---|---|
| A client posts its own numbers | The form carries no numbers; the server recomputes and a test posts forged fields and checks they are ignored |
| Two approvals for one week, or a row rewritten | One decision per week, append-only open flag, validated read-back; tests for double approval and a corrupted line |
| Writable filesystem needed (static hosting cannot append) | Local and `next start` work; the deploy choice is P4 and is flagged in the ADR; ledger path is configurable |
| "Ringgit at stake" read as a saving | Labelled "at stake", with a note that nothing has been measured |
| The templated reply reads as AI output | Marked as a template; the pitch says a model writes these in production |
| Server actions in Next 16 are unfamiliar | Read `node_modules/next/dist/docs/` before writing one (AGENTS.md) |

## Definition of done

- Approve and Change write one validated ledger row each; the board's tile and the decisions page reflect it; a second approval of the same week is refused; a forged number in the form is ignored.
- Drafts and answers contain no number outside the registry (tested); the page says the reply is not sent.
- `npm test`, `lint`, `typecheck`, `build`, `check:literals` pass; `/decisions`, `/ledger`, `/ask` and the board viewed at desktop and phone width; one real approval run against the production server and the ledger file inspected.
