# Plan — P1 Board

> Phase P1 of `refdocs/plant-load-radar-PRD.md` §6. Execution doc: `refdocs/execution/2026-10-08-p1-board.md`.
> A plan says **what and why**. The execution doc says **how and in what order**. Keep them separate — when they merge, both stop being read.

## Why this exists

The pitch's second and third promises are "one board" and "a recommendation in ringgit the scheduler can approve". P0 built the maths and the data; nothing a scheduler can look at exists yet. P1 turns the committed scenario into the screen on deck slide 9: spare or short capacity by week, the weeks that need a decision, and for each one a recommendation that shows the ringgit on both sides. It is also the first place where the rule "every displayed number comes from the calculator" can be broken, so P1 must make that mechanically checkable in the UI, not just in the core.

## What's already covered (no work needed)

- The rule, fairness rules, cost functions, pre-build planner (`planPrebuild`) and the pricing bridge from a scenario to the core (`src/data/scenario.ts`) — P0.
- A committed scenario in which week 43 is the only contested week and the deck's story plays out (P0 tests).
- ADR D-13 defines what "value at stake" means; this phase displays it, it does not redefine it.

## Scope

**In:**
- **Planner (`src/core/planner.ts`):** per-week balance (spare or short, m³); for each contested week the rule's recommendation (who is served, who moves where, the ringgit on each side); and the **pre-build alternative** — what the quiet weeks before it could cover within a stock cap, and what the rule would then decide.
- **Planner settings in the data:** a stock cap, as an assumed parameter with a provenance note, carried through params → scenario.
- **A board view-model (`src/data/board.ts`)** that turns a scenario into exactly the figures the screen shows, and nothing else.
- **The board screen** at `/`: header with the plant and weeks, an always-visible banner that the data is synthetic and illustrative (not Chin Hin's), KPI tiles that have a real source today, a six-week-plus chart of spare/short m³, the recommendation card for the contested week with the pre-build alternative, and a table of that week's committed orders and new requests.
- **UI number-honesty test:** every number in the rendered board is a figure produced by the view-model, which is built from the calculator.
- Visual check in a real browser engine (screenshot), at desktop and phone width.

**Out (and why):**
- **Approve / Change doing anything.** Approving writes the ledger and must be human-gated — P3. In P1 the buttons are visibly inert and say so; a button that looks live but is not would be a lie.
- **Orders inbox, intake, agents, WhatsApp text** — P2.
- **"Protected this month" and "Orders to check" tiles** — they have no source until the ledger (P3) and intake (P2) exist. Showing a number would be fabricating one; the tiles are left out, not stubbed with zeros.
- **Ask the board, huddle brief, customer reply** — P3 (Writer agent).
- Auth, multiple plants, other products, editing data in the UI (D-11).
- Holding-cost estimate for pre-build: needs an AAC price (a placeholder) and a carrying rate (low-authority range); showing a ringgit figure would overstate precision. P1 shows m³ and the stock cap only.

## Approach

Keep the screen dumb. `planner.ts` and `board.ts` do all arithmetic and formatting decisions; the React component receives a finished `BoardModel` and only lays it out. That makes the page testable without a browser (render to static markup and inspect it) and makes the honesty rule checkable: the test extracts every number from the rendered text and fails if one is not in the model's allowed-figures list. The page itself is a server component that loads the scenario through the manifest-enforcing loader. No chart library: the chart is a small hand-written SVG (a bar per week, up for spare and down for short), which is cheaper to ship and to verify than a dependency (rule 8). The pre-build alternative is computed, not asserted: shift the quiet weeks' production into the contested week's capacity, re-run `decide`, and show the new outcome next to the baseline so the scheduler sees both.

**The design question the plan settles:** with a generous stock cap, pre-build can cover the whole week-43 shortage, which would dissolve the A-versus-B contest the pitch is built on. That is a truthful outcome, not a bug, and the board must not hide it. So the recommendation card leads with the rule's decision *given today's capacity*, and shows pre-build as a clearly-labelled alternative with its stock cost in m³. The stock cap is therefore a visible, assumed parameter, and the synthetic scenario's cap is chosen to be tight enough that the contest remains (the deck's own text says pre-build happens "within a stock limit so we don't tie up cash"). The pitch can then say honestly: the rule decides what pre-build cannot cover.

## Risks & unknowns

| Risk / unknown | Confidence | Mitigation |
|---|---|---|
| Next.js 16 server-component page reading local files at build time | Medium — standard pattern, not yet done in this repo | Task 3 reads the current Next.js docs on data fetching and on the `app/` conventions first; confirm with `npm run build` |
| Testing a component with `react-dom/server` inside vitest (node environment, TSX) | Medium | Task 4 starts with a one-component spike; the Next docs say vitest cannot render **async** server components, so the board component is synchronous and receives its model as a prop |
| Hand-written SVG chart is readable, accessible and responsive | Medium | Load the `dataviz` skill before writing it; give it text labels and a table fallback (the week table), not colour alone; check at phone width |
| Rendered-text number extraction is brittle (dates, week labels, "m³") | Medium | The test strips known non-figure tokens (week labels, ISO dates, units) and has its own unit tests; when it fails it names the offending string |
| Headless browser available for a screenshot (Playwright MCP is disconnected) | Medium | Microsoft Edge ships with Windows 10; try `msedge --headless --screenshot` first; fall back to rendering the static HTML and reading it |
| A tight stock cap that keeps the contest is itself an assumption that shapes the demo | High, and it is the point | Mark it ASSUMED in the provenance; state in the card what the contest looks like with and without pre-build |
| Pricing in the board duplicates `toPricedRequests` | Low | Reuse `toPricedRequests` and `decide`; the view-model adds no new maths beyond sums and differences, each tested |
| Money display rounding and currency formatting differ by locale | Low | One formatter in `board.ts` using fixed `en-MY` formatting, unit-tested; the core stays unrounded (ADR on rounding in P0 plan) |

## Definition of done

This phase is done when every line below is true and has been *observed*:

- `npm test`, `npm run lint`, `npm run typecheck`, `npm run build` and `npm run check:literals` all pass, with the counts recorded in STATUS.
- Running the planner on the committed scenario reports week 43 as the only contested week, short by 2,000 m³; the rule serves Project A and moves Contractor B to week 44; the ringgit on each side equals the calculator's (A = 7 × the daily rate; B = its margin).
- The pre-build alternative for week 43 is computed from the scenario's stock cap, reports how many m³ it can cover and what the rule would then decide, and a test shows the numbers change when the cap changes.
- A test renders the board and fails if any displayed figure is not in the view-model's allowed list; a second test shows it *does* fail when a stray number is planted.
- The page shows the synthetic/illustrative banner, and a test fails if it is removed.
- The Approve and Change controls are inert and labelled as arriving in P3; a test asserts no handler writes anywhere.
- A screenshot of the running page at desktop and phone widths was looked at, and the issues it showed were fixed or recorded.
- `ui-reviewer` has reviewed the page against deck slide 9 and its *broken* and *inaccessible* findings are resolved.
